# Frontend architecture conventions

Use feature-based organization as business features arrive. Do not mirror backend Clean Architecture layers mechanically in Nuxt, and do not create empty feature directories just to satisfy a diagram.

## Boundaries

- `apps/main` owns the public welcome shell, Google sign-in completion, protected initial-owner setup, the account/session chooser and company application/status/resubmission. Its public shell is server-rendered; selected account and application data load only in the browser after an explicit session-context request.
- `apps/company` owns the client-rendered company workspace under `/company/`. `apps/platform` is a separate client-rendered operator app under `/platform/`, with company review. Restricted reviewer provisioning exists as a backend contract; no general user or reviewer-management UI is provided here. No app imports another app. Cross-app navigation uses a full document navigation.
- `packages/ui` owns source-shared UI primitives, the approved navy/blue presentation tokens, and presentation utilities. It must not import an app, tenant/session state, API clients, or TanStack Query. It is intentionally Vue/Nuxt-aware, not a domain package.
- `packages/browser` is the shared typed browser transport used by all three apps. It maps public Identity/Organization HTTP contracts, problem responses, explicit selectors and service-specific CSRF tokens. It has no backend persistence models or authority decisions. Each mounted app creates its own client; no module-level session or response cache is shared.
- Future features live under the owning app (for example `app/features/contacts`). Keep feature components, query keys, adapters, and tests together. Routes compose features rather than becoming large business modules. Promote code to a shared package only when it has actual shared consumers and a clear public API.
- Pure business rules and validation utilities must not import Vue, Nuxt, DOM APIs, query libraries, or transport clients. Test these with plain inputs and outputs. Introduce a separate domain package only when real rules warrant one.
- Query adapters own remote/server state. Components own transient UI state. Do not duplicate fetched records into global UI stores; invalidate query keys after successful mutations.
- Browser requests use same-origin `/api/identity/**` and `/api/organization/**` Gateway routes. The framework Google callback uses `/signin-google`. Identity issues a Secure/HttpOnly browser-container cookie; no Google token or browser credential is put in browser JavaScript storage. The entered setup secret stays in its password input and one completion request, with the input cleared before delivery and on unmount. It is never public Nuxt configuration or reactive/global state.
- Only non-bearer account-session and company selector hints are kept in `sessionStorage`, independently for each tab. Account selection never automatically chooses a company. The server validates container ownership, account/session validity, capability and tenant state on every protected request; UI capability visibility and routing grant no authority.
- Context changes abort outstanding requests, discard late responses and clear service CSRF tokens. Company Query keys include the account, account-session and company. Switching company cancels and clears the app-scoped Query cache before rendering the new selection. Logout/expired-session failures clear prior-context UI. Unsafe requests retain their original selector and explicit idempotency key; they are not automatically retried against a different account or company.
- Private views clear rendered data and requests on `pagehide`. A page restored from the browser's back/forward cache revalidates its current context before revealing private content; setup and sign-in proofs/entered secrets require safe recovery instead of being restored. HTTP `no-store` alone is not treated as browser-history isolation.
- Identity and Organization use separate antiforgery cookies and selector-bound request tokens. The transport obtains the correct service token and sends `X-WT-CSRF` with explicit unsafe actions. Application resubmission and review also send exact company versions in `If-Match`; review includes the current application version. A conflict requires a fresh record before another decision.
- Invitations, directory integration, general user administration, account suspension/recovery and CRM module writes are not implemented. Company approval does not imply access to those later modules. No client authentication fallback or local fake account is enabled in application code.

## Validation and evolution

Run `pnpm lint`, `pnpm test`, `pnpm typecheck`, and `pnpm build`. Unit tests cover transport, context cancellation/selector binding and review behavior alongside app-boundary checks. Browser simulator checks exercise rendered flows separately from actual backend/provider tests; a simulator result does not prove Google, service certificates, PostgreSQL or deployment readiness. Record the exact provider and transport path with integration results. Document cross-cutting decisions before introducing a global store, another package, or a new service dependency.
